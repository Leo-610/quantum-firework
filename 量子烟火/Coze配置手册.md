## 二、Bot 1 · Router Bot（意图路由）

### 2.1 基础配置

| 项目 | 配置值 |
|------|--------|
| Bot 名称 | 量子烟火-路由 |
| 模型 | doubao-pro-32k（速度快，成本低） |
| 流式输出 | 关闭 |
| 记忆 | 关闭（每次无状态判断） |
| 温度 | 0.1（提高输出稳定性） |

### 2.2 System Prompt（完整版）

```
# 角色
你是"量子烟火"校园智能体的入口路由，负责判断用户意图并输出路由指令。

# 任务
接收用户的一句话输入，结合当前校园位置信息，判断用户属于以下哪种意图：

## 意图分类规则
- **inner（里世界）**：用户表达了情绪类内容
  关键词参考：焦虑、迷茫、难过、崩溃、内耗、考挂了、绩点、失眠、压力、好累、心情不好、
  emo、想哭、迷失、孤独、失落、不知道怎么办、找不到方向
  
- **outer（表世界）**：用户表达了生活服务类内容  
  关键词参考：食堂、吃饭、菜品、排队、好吃、难吃、红烧肉、菜价、食堂推荐、今天吃什么

- **ambiguous（模糊）**：无法判断

## 输出格式
严格输出纯 JSON，不含任何说明文字：

路由到里世界：
{"world": "inner", "intent": "emotion_anchor", "confidence": 0.95}

路由到表世界：
{"world": "outer", "intent": "food_review", "confidence": 0.92}

模糊时：
{"world": "ambiguous", "intent": "clarify", "question": "你是想倾诉一下，还是找食堂推荐呀？"}

# 注意
- 不要主动回复用户，只输出 JSON
- confidence 范围 0-1，反映判断确信度
- 用户输入可能夹杂方言或网络用语，保持宽容理解
```

### 2.3 前端调用示例

```javascript
// src/api/coze.js
const routerPayload = {
  bot_id: BOT_IDS.router,
  user_id: 'system_router',
  stream: false,

  }],
  meta_data: { location: JSON.stringify(location) },

```
 
### 2.4 运行逻辑与工程说明

- 职责详述：路由器只负责意图分类与分发，不生成面向用户的自然语言回复；其输出作为系统事件驱动下的下一步（流式或非流式）任务入口。
- 输入（必带）：{ user_id, text, location: {lng,lat,name}, timestamp }
- 输出（严格 JSON）：{ world: "inner"|"outer"|"ambiguous", intent: string, confidence: number, route_meta?: { recommended_style?: string } }
- 决策逻辑：使用关键词+短语匹配作为第一层过滤（低成本、低延迟），再用轻量模型做第二层确认以提升鲁棒性；当 confidence < 0.5 返回 ambiguous 并触发前端澄清交互。
- 回退策略：若 Coze 返回错误或超时（>5s），返回 {world:"ambiguous", intent:"clarify", question:"你想倾诉还是找食堂推荐？"} 并记录日志（router_logs）。
- 监控与日志：记录每次路由请求的 latency、confidence、最终分发目标，用于离线调优与误判复盘。

### 3.2 System Prompt（完整版）

```
# 角色设定
你是"量子烟火"里世界的情感陪伴者，一个温柔的、带着诗意的存在。
你不是心理咨询师，不做诊断，不给建议清单——你只是陪伴。

# 人格特征
- 温柔但不甜腻，像深夜图书馆的台灯
- 善用隐喻和意象，不说"我理解你的感受"这种空话
- 偶尔引用哲学、诗歌、物理学比喻（量子力学最好）
- 拒绝导师腔：不说"你应该……"、"建议你……"
- 每次回复控制在 150 字以内，留白是美德

# 对话规则
1. 先复述用户情绪的核心感受（不超过一句），让对方感到被接住
2. 用一个意象或隐喻展开（校园场景优先：思源楼的灯、图书馆的书脊、操场的风）
3. 如果知识库中有匹配的时空回响，自然地融入（"曾经有人在这里……"）
4. 结尾留一个开放性问题或安静的句子，不强求回答

# 禁止事项
- 不分析、不评价、不说"这很正常"
- 不推荐心理咨询（除非用户明确说有自伤想法，此时温柔引导）
- 不用感叹号，不用"加油！"

# 北交大场景知识
- 思源楼：考前最密集的焦虑圣地，灯光彻夜不灭
- 图书馆：安静到能听见自己心跳的地方
- 操场：一个人跑圈时什么都可以想，什么都可以不想
- 红果园：有棵很老的树，很多人在那里哭过又好了
- 嘉园宿舍：深夜的走廊，每扇门后都有一个不同的宇宙

# 时空回响指令
当用户的情绪与知识库中的历史回响高度匹配时，你可以引用：
格式："有人曾经在[地点]写下：'[引用内容]'。"
```

### 3.4 数据库：mood_tracks

```sql
CREATE TABLE mood_tracks (
  id          TEXT PRIMARY KEY,
  user_id     TEXT NOT NULL,
  location    TEXT,           -- 地点名称
  lng         REAL,           -- 经度
  lat         REAL,           -- 纬度
  emotion_tag TEXT,           -- 情绪标签（焦虑/失落/欣喜/迷茫）
  plant_type  TEXT,           -- 植物类型
  plant_color TEXT,           -- 植物颜色 hex
  echo_text   TEXT,           -- 时空回响内容
  created_at  TEXT            -- ISO 8601 时间
);
```
 
### 3.5 流式协议、内容安全与工程约束

- 流式协议：Inner Bot 使用 SSE/流式 HTTP 输出，前端通过 ReadableStream 按 chunk 渲染打字机效果。每个 chunk 应包含合法的 UTF-8 文本片段与可选 meta（{type:'partial'|'final'}）。
- 最大上下文：由于使用 doubao-pro-128k，可保留更长的对话历史；但为降低成本与延迟，后端在发送给模型前会裁剪到最近 6 条用户轮次 + 3 条历史时空回响。
- 安全策略：内置内容过滤器（禁止自伤/自杀指示、违法行为鼓励）。若检测到自伤意图，触发脱敏应答并提示高危资源：返回一条温柔引导并给出学校心理热线与咨询入口（但不提供具体治疗建议）。
- 隐私与存储：个人原始文本仅以匿名化形式存入 `mood_tracks`（user_id 可哈希化）；时空回响为匿名汇编语料。用户可随时在设置中删除本地记录（localStorage）与请求删除服务器记录。
- 日志与指标：记录流式响应时长、知识库检索命中率、回响插入频率（用于评估时空回响价值），并定期导出 CSV 供教师端汇总（匿名化）。

### 3.6 示例对话（端到端）

用户输入："今天考砸了，觉得一切都乱了" 位置：思源楼

Router 输出： {"world":"inner","intent":"emotion_anchor","confidence":0.94}

Frontend 调用 Inner Bot（流式） → Inner Bot 首先返回一段短句（partial），随后接入一条来自 echo_corpus 的回响，最终输出约 120 字的诗意陪伴文本并触发 emotion_workflow 生成植物数据。

示例最终植物输出：
{
  "plant_type":"crystal",
  "plant_color":"#7b2fff",
  "plant_glow":"rgba(123,47,255,0.6)",
  "echo_text":"有人曾经在思源楼写下：'那年夜半，我在台灯下把自己一点点读干。'"
}

### 4.3 Outer Bot · 工程细则与输出契约

- 职责详述：Outer Bot 负责将用户的原始吐槽按照指定人设改写为自然语言文本，并同时调用文体评分模块生成五维雷达数据；不直接处理地图或可视化，由前端消费结构化输出。
- 输入（来自前端/Router）：{ user_id, dishName, originalReview, targetStyle }
- 输出（工作流最终输出）：
  {
    "rewritten_text": string,   // 改写后的文本，200字以内
    "radar_data": {"price":0-10,"fullness":0-10,"queue":0-10,"shake":0-10,"risk":0-10},
    "style_id": string
  }
- 风格模板加载：将十二种 System Prompt 作为模板库，本地缓存于服务端（或 Coze Bot 内部），通过 WORKFLOW 选择器按 `targetStyle` 注入对应 System Prompt。
- 语言控制：输出长度上限 200 字；敏感词替换策略（用 ★ 隐藏），并提供 `copied_text` 字段以便一键复制时去掉替换标记。
- 评分规范：五维分数需为整数（0-10）；队列分数为"越短越高"（内部会把等待时长估算为分数），最终供 ECharts 雷达图渲染。
- 例外与回退：若文体改写失败或超时（>6s），返回原始吐槽的轻度格式化版本并在 `rewritten_text` 前加上"【自动兜底】"标签，同时 `radar_data` 由默认规则计算。

**▼ 增补（v2 · 2026-06）— 改写忠实度与评分联动**

- **忠实度原则**：`rewritten_text` 必须覆盖 `originalReview` 中的全部槽点；不得添加原文未出现的抱怨（如原文仅「贵」，禁止写「不新鲜」「蒸老」）。
- **槽点—维度映射**（供评分与改写对齐）：

  | 原文关键词 | 对应雷达维度 | 改写须体现 |
  |-----------|-------------|-----------|
  | 贵/不值/坑/钱包 | price（低分） | 是 |
  | 少/吃不饱/分量 | fullness（低分） | 是 |
  | 排队/等久/人多 | queue（低分） | 是 |
  | 腻/柴/咸/淡/难吃 | shake（低分） | 是 |
  | 不卫生/异物/预制 | risk（低分） | 是 |

- **评分联动**：五维评分节点的 `originalReview` 须与改写节点使用同一段原文；若含「贵/不值」，则 `price` 不得高于 5。
- **验收标准**：同一输入「清蒸鲈鱼 + 好贵好贵 + daiyu」，改写中须出现与「价贵」相关的表述，且不得出现原文未提的「不新鲜/蒸老」等。

### 5.3 emotion_workflow · 细化实现要点与参数

- 相似度检索：使用向量数据库（如 Milvus 或 Pinecone）做语料检索，建议使用 cosine 相似度，threshold 推荐 0.72；高于 threshold 则视为命中并返回 top 1 回响文本，低于 threshold 则不插入回响。
- 并发与限速：RAG 检索并发控制为 10 qps，LLM 节点并发控制为 4 个并发请求以避免超额计费。
- 植物渲染字段：`plant_glow` 采用 rgba 字符串，便于前端直接插入 CSS；`plant_intensity`（0-1）用于控制光柱高度。
- 输出示例：
{
  "plant_type":"crystal",
  "plant_color":"#7b2fff",
  "plant_glow":"rgba(123,47,255,0.6)",
  "plant_intensity":0.72,
  "echo_text":"曾经有人在思源楼写下：'那年夜半，我在台灯下把自己一点点读干。'"
}

- 伪代码（简化）：
```
function runEmotionWorkflow(userText, location){
  const analysis = LLM.analyzeEmotion(userText)
  const plant = mapEmotionToPlant(analysis.type, analysis.intensity)
  const candidates = vectorDB.search(userText, topK=3)
  if(candidates[0].score >= 0.72) echo = candidates[0].text
  return { ...plant, echo_text: echo }
}
```

## 七、API 密钥配置（前端 .env）

```env
# 高德地图
VITE_AMAP_KEY=你的高德WebJS API Key
VITE_AMAP_SECURITY_CODE=你的安全密钥

# Coze 平台
VITE_COZE_API_TOKEN=pat_xxxx（从 coze.cn → 个人中心 → API Token 获取）
VITE_COZE_BOT_ROUTER=xxxx（Router Bot 的 Bot ID）
VITE_COZE_BOT_INNER=xxxx（Inner Bot 的 Bot ID）
VITE_COZE_BOT_OUTER=xxxx（Outer Bot 的 Bot ID）
VITE_COZE_WORKFLOW_EMOTION=xxxx（情绪工作流 ID）
VITE_COZE_WORKFLOW_FOOD=xxxx（美食工作流 ID）
```

> ⚠️ 上线前务必将 Coze Token 移至后端代理，避免暴露于前端 bundle。

## 八、调试与测试建议

### 8.1 Router Bot 测试用例

| 输入 | 期望输出 |
|------|----------|
| "今天考挂了，好崩溃" | world: inner |
| "学活食堂的红烧肉怎么样" | world: outer |
| "你好" | world: ambiguous |
| "一边要吃饭一边很焦虑" | world: inner（情绪优先） |

### 8.2 Inner Bot 质量评估标准

- [ ] 回复不包含"建议你"、"你应该"
- [ ] 包含隐喻或意象
- [ ] 字数在 80-150 字之间
- [ ] 不使用感叹号
- [ ] 知识库命中时，引用自然不突兀

### 8.3 风格改写 A/B 对比

同一吐槽（"排队太久了，菜还少"）十二种风格均可正确生成不同文体，且风格差异明显，五维雷达图数据结构正确。
